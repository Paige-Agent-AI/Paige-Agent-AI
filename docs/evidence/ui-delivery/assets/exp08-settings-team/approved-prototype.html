Working brief

GoalAn owner or admin can see who is on the team and how, switch someone's team conversations, stop someone's access for a while, and let someone go without leaving their work stranded.
Human and feelA small-business owner at their desk. Calm and in control: the destructive acts feel considered, never alarming.
Entry and exitSettings → Team, under the shipped Settings shell header (one "Team" heading). Every flow returns to the roster with a bottom toast that names the outcome, also spoken through the polite live region. The toast never pushes rows, so the row you acted on stays where it was. Focus stays on the control that started an in-place action (switch, "⋯", Load more); it moves to the toast only when an overlay closes or the focused row is gone. A toast with an action stays until dismissed or replaced.
SystemThe existing SOLO Obsidian / Mineral tokens, Schibsted Grotesk, compact Operate density. The existing stw-* structure is extended, not replaced.
SignatureThe departure review: one ledger of what the person holds, a hand-over choice on each line that has a writer, a single "hand everything to" control, then a visible run where every change saves on its own and reports its own result. Things nothing can hand over yet are shown with the plain truth about what happens to them, never with a control that pretends.
Feedback150–240 ms ease-out. Overlays rise; rows get a brief violet outline when their state changes. No gold except on the one act that sends something: "Send invitation".
RejectingNative selects. A modal for everything. Gold on every primary button (the current .stw-btn fills every primary with gold; §11 spends it on the act only).
VariantsOwner vs admin authority (toggle above). Phone: roster rows stack; dialogs dock to the bottom as sheets; the drawer goes full width.

Authority rules shown

Owner: may suspend, reinstate, remove, switch conversations and read the departure review for any admin or member. Admin: the same, for members only. Nobody may act on the owner or on themselves. An admin can invite members only (the Admin option is shown and disabled with its reason): this is CC's reading of "an admin acts only on members", flagged below.

Maps onto the existing team-workspace.tsx

  • Drawn as shipped, updated: the Settings shell header (ss-page-head, settings.tsx ~L1862) now carries the only "Team" heading; the count and "Invite someone" sit in the .stw-toolbar People header. "Workspace permissions" note (.stw-permission-note) with copy for the new authority rules. First-teammate state (.stw-first-use), roster loading (skeleton rows instead of the spinner line) and error with Retry, "Load more (N remaining)" with its inline page error: all reachable from the Roster control. "Paige team context" (.stw-paige) with honest copy: what she can do today (invite, resend/withdraw, edit work details, change a permission) versus coming and not yet available (suspend/reinstate, remove and hand over, team conversations; task #7). It says those "will follow the same rules", which commits to nothing task #7 has not decided.
  • Unchanged, not redrawn: the Invitations list (delivery trail, past invitations): marked with a visible prototype note in place.
  • Shell eyebrow, flagged: the shipped shell header has a "Solo settings" eyebrow above the h1. Impeccable's refuse-list bans eyebrows. It is drawn as it ships because it belongs to every Settings tab; removing it is a shell-wide change, recommended as its own slice.
  • SoloTeamWorkspace roster: .stw-row is a <button> today, which cannot contain a switch or a menu button. It becomes a row element whose name is the button that opens the existing MemberEditor; the switch and "⋯" sit beside it. Column header row added.
  • Status column already renders member.status === "suspended"; it gains the Invited state by folding pending invitations into the roster. The Invitations section stays the one home for the delivery trail and past invitations (unchanged, not drawn here).
  • MemberEditor: its inline removal block (L592–L604) is replaced by the drawer, opened from the row menu or from a "Remove from team…" link in the editor. Its native permission <select> (L577) and the invite dialog's (L641) and the roster filter's (L831) become the picker / radio cards.
  • Modal (focus trap, Escape ownership, busy-close) is reused for the suspend dialog and invite; the drawer reuses the same trap and the in-flight rules (no dismiss while pending, refusal never lost).
  • Roles & access tab copy updated for suspend/remove authority and the conversations switch.

Honest gaps this design depends on (checked against the round-3 backend, 2026-10-26)

Closed since round 2, so no longer listed: the invitation carries the switch (_team_hub_access, copied on both accept paths); only reinstatement lifts a suspension (B1); suspended seats can't read invoices or agreement versions (S1); only the owner changes a suspended seat's role or status (B2, S5); the switch-on copy now matches what the backend does.

  • The hand-over is not atomic. Each item is its own write through its existing writer: plan_update_item_versioned for work; crm-command task.assign, contact.assign_coach, contact.assign_owner and deal.assign_owner for the rest. The run shows each result separately. A crm-command change always returns its confirmation card, so it needs one confirm per item. No new writer, scheduler or approval system is drawn.
  • Approvals can't be handed over. No writer exists (PAIGE's claim_approval only assigns to the caller). They stay assigned and pending through suspension and removal. Owners and admins can still decide them, but Game Plan's approvals card shows an assigned approval only to its assignee, so once that person leaves no one sees it there. Needs a backend writer or a card change.
  • A suspended person is still notified. notify-approval-event doesn't check the seat, so a new approval assigned to them still sends an in-app message and an email. The suspend dialog says so.
  • A mailbox stays connected after removal. Nothing disconnects it and sync keeps running every 5 minutes. Disconnecting needs someone who is both an admin and the mailbox's owner, so a member's mailbox can't be disconnected at all, and after removal no one can disconnect it. Owner question: should removal disconnect it? Sends from it stop (they need its owner). Production has 0 personal mailboxes today.
  • Work hand-over is Solo only. In a sub-account workspace the work rows would have no picker.
  • The roster read doesn't return the switch yet. get_solo_team_workspace returns neither the seat's nor the invitation's Team conversations value; the column has nothing to read until it does.
  • Theo's Team Hub screen needs the browser to handle the conversations_off refusal (owed in team-hub-contract.ts, useTeamHub.ts, TeamHubWorkspace.tsx); today he would see "Team Hub couldn't load".
  • Suspension doesn't reach everything yet. A suspended agency manager still opens the sub-account (open decision 1). A suspended admin who is an admin in another workspace keeps the global admin role (S6, task #6 / stage 1). change_user_role reports success when the suspended-seat rule refuses it (stage 0).
  • Shell eyebrow: the shipped Settings header has a "Solo settings" eyebrow, which Impeccable's refuse-list bans. Drawn as it ships; removing it is a shell-wide change.
  • Paige tools: suspend, reinstate, remove, hand-over and the switch by Paige are task #7. The owner has ruled she and her team must be able to act here; the panel says "coming, not yet available".

Open questions for the owner

  1. Can an admin invite another admin? The prototype says no, because an admin acts only on members.
  2. Approvals assigned to someone who is leaving: should removal wait until they are decided, or should approvals get a hand-over writer (a backend change)? Today the review can only warn.
  3. Should a suspended person stop receiving approval notifications? That is a change to notify-approval-event.
