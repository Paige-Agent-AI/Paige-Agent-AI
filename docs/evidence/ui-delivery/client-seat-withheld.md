## User job and state map

A client asks; PAIGE answers. The answer and every thought line a client can read are held until the turn ends and read against the vocabulary of that turn (R1, text the handler vouches for). Clean: released exactly as before. A finding: the whole turn is dropped, the client reads the approved sentence (with "Anything I'd already finished is saved" only when a tool reported a save), the thread keeps that sentence, the portal is told the turn was withheld so it keeps no document summary, and on the credit-report path nothing is extracted. The scroll owner is the chat's message list, unchanged.

## Review and limitations

- An independent §39 review of the diff found one MAJOR and one MINOR, both fixed, and a second read of the fixes found a test gap and one more unread channel, both fixed (30.31: an evidence-free client turn is held; 30.32: a confirm card's summary is read). The first round's findings: a tool refused to a client seat still rendered an action step, which for buying a number carried the model's own argument onto a channel the check does not read (fixed, 30.29); and holding every client turn had also sent every client turn through the scope re-check (fixed, 30.0 and 30.30). It confirmed both vouched blocks are server-written end to end and that owner turns are byte-identical to the base.
- Limits: a clean result means none of the known vocabulary, and a paraphrase passes; a key or block name that appears only in a block nobody has vouched for is not caught; for a genuine portal client the vouched authority block usually renders nothing, so their vocabulary is mostly tool names, tool results and the document instruction; a lowercase id or Postgres wording from the client's own words can withhold an answer; a caller whose tier cannot be resolved is treated as a client seat; action steps are not read (the only one a client can see is a fixed label); a confirm frame carries its tool's name, server-written and unread (the portal does not render it); the document path's final-line sentinel is untested. Found in passing, not R3's: a schema-correct `update_client_data` card names the array's indices instead of its fields.
