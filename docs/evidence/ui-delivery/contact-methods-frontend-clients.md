## Review and limitations

Onboarding Step 1 collects a phone that is not stored: a linked client may not call upsert_contact (staff only) and no client-self address RPC exists; the old UPDATE of clients.phone matched no UPDATE policy for a linked client, so it did not store it either. The missing piece is a backend RPC. Authenticated browser behavior is UNVERIFIED in this environment.

Round 2 (stacked on the concurrency branch). Every address write in this lane now names the list it
was built on: the Edit contact dialog and the internal client file pass the list the page read, and
Field Ingestion passes the list the proposal was built on (an explicit `expected_contact_methods`,
else the proposal diff's `contact_methods.from`, else the list read at approval). Each write carries
the contact's own workspace. A save the database refuses as stale is shown as "changed since this
page loaded, nothing was saved"; nothing else on the record is written, and a Field Ingestion
proposal stays unapplied. Production has no `propose_client_update` proposals in any status (read-only
count), so both proposal shapes are proven by tests only.

Round 3. Paige's `propose_client_update` (lane 6c) no longer stores a frozen copy of the resulting
list; it stores the change asked for (`address_intent`: primary, add or replace) and the list it was
built on. Field Ingestion now applies exactly that, with the server's rules, mirrored in
`src/lib/contact-method-intents.ts` and pinned to the server planner by fixtures produced from it:
primary is planned on the list held now and refused only if the primary it displaces is no longer the
one the proposal was built on; add keeps every address held (the browser has no unchecked add, so it
merges onto the list read now, writes checked, and rebuilds up to twice if another save lands in
between); replace names the built-on list. The retired full-list format is refused as the server
refuses it (production holds no proposals at all, read-only count, so nothing in flight is affected).
The row patch is checked before anything is written, the row update is scoped to the proposal's
workspace and must return the row, and a failed row update puts the address change back, checked
against what it wrote. Field Ingestion has no importer in src today; this path is reachable only once
it is remounted.

Round 4. Lane 6c tightened its stale rule (8742b9fbc): a proposed primary or replacement is
written only onto the very list its preview was built on, compared the way the database compares
lists (public.contact_methods_fingerprint), and the write names that built-on list. Field Ingestion
now does the same, so a proposal gets the same answer whoever approves it: an address added,
removed, relabelled or reordered since the proposal leaves it unapplied with nothing written, and the
approver is told to have Paige propose it again. Round 3's "an address added after the proposal is
kept" no longer holds for primary. Both planners are pinned to fixtures regenerated from 6c's
current planner.

Still owed, not built here: an assigned cs_rep or sales_rep could change a contact's email or phone
through the old direct row UPDATE, and `upsert_contact` requires admin or super_admin, so those roles
are now refused on the Edit contact dialog and the internal client file (both unreachable today; a
§58 owner decision before either is remounted). The Paige customer picker's email search reads at
most 50 matching address rows before its 50-contact cap, so when more than 50 addresses match the
typed text a contact matching only by email can be missed.
