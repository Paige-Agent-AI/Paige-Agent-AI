- Releases need a second active team member and a standalone business (D2/D3); file artifacts cannot be released.
- No owner delete or rename (D7); the customer cannot delete or rename (D8).

- The release flow's four choices use the Select primitive (round 3); the Operations Work filter and the CRM stage review, outside this slice, keep native selects.
- A service-role move of a shared file withdraws it with no audit row; nothing does that today.
- A member can rename a shared file over REST (verifier MINOR-J, probe B6c): the incumbent update policy admits `original_filename` and `mime_type`, so the client sees the new name with no audit row. It does not change which object they can open (the matrix asserts the rename gains nothing), and the type the browser receives comes from the stored object. Filed with the `client_files` table-policy follow-up below, which would route a shared file's rename through the owner's writer.
- A business admin's direct INSERT may claim `upload_state = 'ready'` without the owner finish's object check (the incumbent insert policy does not constrain it). Sharing such a row still goes through `client_file_set_client_share` and is audited, and storage serves only an object the row's uploader owns; filed with the same follow-up (round-5 matrix observation).
- Shared files stay with the contact (verifier round 5, P2 — a product decision for Slice 7): when a person's access to a contact ends and a different person accepts a new invitation to the same contact, the new person sees the files the business shared to that contact before, while it belonged to the previous person. The share writer authorized each of those shares for the contact, not for a login, so this is the defined behaviour; the former person's own uploads do not follow (round 6, pgTAP section 17). Whether an end should withdraw shares, or a re-invite start the contact over, is for Slice 7 and the owner to decide.
- `enforce_clients_linking_integrity` lets a signed-in caller link a client record to their OWN login, including a record already linked to someone else (it only refuses a foreign link or an unlink). It already exists on main. It is the lever verifier probe P6 used: an owner self-links an unconnected client, uploads through the customer's upload pair (which passes `FILE_CLIENT_UPLOAD_PROVENANCE`, because the uploader is now the record's linked login), ends access and lets the real client join. Round 6 closes the leak at the read (the client never sees an upload made by another login, the owner's included), but the lever itself — and the lock-out of a customer whose record a business admin moves onto their own login — is filed for Slice 7 and the `client_files` policy follow-up.
- P8 is closed in round 6: a customer's REST read no longer returns another login's upload on their own contact, and its object can no longer be opened (pgTAP sections 11, 12, 12b and 17).
- `client_files` table-policy follow-up (not in this slice; verifier rounds 1–3): the incumbent "Uploader or admin delete files" policy lets the uploader, or a member of the business who holds the global admin role, delete a SHARED file over REST. That takes it away from the client without `client_file_set_client_share` and with no audit row (verifier probe A7, re-confirmed on the round-4 migration: the delete removes 1 row). It is not new — main allows the same delete — and it is filed with the other incumbent-policy findings on this table, which the verifier's round-3 probes still reproduce: P1/P11, the same global-admin member can read an internal file's row and its Storage object (P8, a customer reading another login's upload, was in this list and is closed in round 6, above). The fix is one migration that re-keys the staff policies on this business's membership (§59) and routes a shared file's delete through the share writer.
