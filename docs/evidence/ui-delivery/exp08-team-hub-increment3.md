## User job and state map

- Purpose and audience: active teammates of one canonical SOLO workspace. Primary action: Send, which stays disabled until every chip is ready (or refused chips are removed).
- Chip lifecycle: client precheck (type, name, empty, over 10 MB, 5 per message) → `team_hub_begin_file` → upload to the server-built path → `team-hub-file` finish (the real-type check) → Ready, or refused with the reason, or failed with Retry (same client request id, so one record).
- File rows: a type glyph or an image thumbnail from its own 60-second URL; Download mints a fresh 60-second attachment URL on every click.
- Scroll owners: the conversations list, the stream and the thread body. The chip tray has no scroll of its own (see defect 2).

## Review and limitations

Defects seen in the frames and measured, reported and NOT fixed here (this lane does not edit `src/`):

1. **Adding chips does not keep the stream on the newest message.** The tray grows the composer from below, the stream's scrollTop stays where it was while its scroll range grows (1536×770: top 575, range 715 → 789; 390: top 771, range 931 → 1074), so the latest file rows slide under the composer (ev-state-unpinned-1536-dark.png, ev-state-unpinned-390-light.png). The stream was also 140–160px short of its end before any chip was added; the cause was not established here (one possibility, untested: the task cards grow when their Operations read lands after the initial scroll).
2. **The chip tray does not reflow at 200% zoom.** With seven chips in a 640×400 CSS px viewport the composer is 520px tall, nothing scrolls it, and the paperclip, hint and Send row sit below the viewport (Send's bottom at y=655); with two chips it fits but the stream is one author line high (harness/probe-report.json, ev-zoom200-1280-chipstates-dark.png, ev-zoom200-1280-chips-light.png). Increment 2 fixed the same class of problem for the task preview with a scrolling body.
3. **File rows squeeze their name on the phone.** At 390px the full-width "Download" button keeps its label, so the name column shrinks to about eight characters ("Kickoff-…", "Brightlin…") and the type · size line breaks over two or three lines, including inside "1.8 MB" (ev-390-files-*.png).
4. **Announcements can overwrite each other.** The hub has one live region; when the double answers within the same frame, "Uploading N files" is replaced by "File ready" or a refusal before it renders, so the harness never observed it. With real network latency the gaps may separate them; a real screen reader was not run.

Seen and left as is: refused chips' sentences wrap to two or three lines inside a 248px chip at 1366; the sixth file in one pick is refused "5 files per message" even when the other five are later refused by the server (the count is taken at pick time, as the contract's client precheck describes).

Limitations: every item in UNVERIFIED above. The harness frame is not the tenant shell and the doubles are not the database, Storage or the edge function, so none of these frames or drives is authenticated runtime proof.
