Why two steps, and why the row is created with no key

oauth_begin acts on a connection that already exists — it reads that row’s address to run discovery against it. So the row is created first, with no credential at all.

That is not a placeholder. A row counts as configured when it has an address and an auth kind of none/url — which is exactly what oauth_begin requires and refuses without. Creating it as oauth up front is impossible on purpose: that bundle demands a token, an issuer and a client id, and those are the very things signing in is about to produce.

This particular case — a server echoing the credential back — is refused outright rather than stored.

The server’s own rule, said earlier

The writer refuses a bearer or header credential under 12 characters. Before this slice that came back as a generic “that didn’t go through” after a round trip, because the code had no copy mapped to it at all.

The guard is scoped exactly as the server scopes it — bearer and header only. It is not applied to an OAuth token (provider-minted, and the server deliberately does not gate it) nor to an n8n API key (which never reaches that check). Guarding either would be the client inventing a rule the backend does not have.

One sentence could not be honest for both kinds of tool

Turning a tool off clears its key but leaves its sign-in type alone. For a tool you signed into, that means Re-key never appears — there is nothing left to re-key with. For a tool you pasted a key into, Re-key is exactly how you switch it back on.

So the advice moved out of the shared error message and into the panel, which is the only place that knows which tool it is holding. Check now and Sign in again are gone from this screen too: on a turned-off tool the server can only refuse them, and a button whose one outcome is a refusal is worse than no button.

What this prototype is, and is not

Is: the flow shape, the step order, the state set, and the exact owner-facing copy — enough to judge the wording and the journey before anyone signs in anywhere.

Is not: runtime proof. Every transition here is scripted. Nothing contacts Supabase, the gateway edge, or a provider. The authenticated drive on the live platform is still owed and is recorded as PROOF OWED in the PR — this page does not discharge it.
